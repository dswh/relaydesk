Teaching overview

A failed customer follow-up creates repeated engineering work. We turn that work into explicit instructions, connect them through feedback, and follow one RAG improvement loop through seven steps. After review, a new question starts fresh checks. Learners then design a loop for one task of their own.

Learner outcome: Set up an allowed change, a check, a review point, and a rule for continuing when inputs change.

Proof: A written loop agreement, saved evidence from a run or replay, and an explained next decision.

Hands-on: Slides 17 to 30 are the fourteen-slide guided demonstration. Slides 38 to 41 guide the learner exercise.

Slide 1. Loop Engineering

Think about the last task you gave a coding agent.

It made a change. You checked the work. Then you had to tell it what to do next.

Today, we will look at how to arrange those next steps in advance.

The aim is to let the work continue using evidence, with clear places to stop and review.

Before we look at an example, let me briefly explain the kind of work I do.

Slide 5. What are we engineering around the agent?

That is what we are designing when we build a loop.

We give the agent a result to reach and a way to check the current state.

We say what it may change.

Then we decide how the last result should lead to another attempt, a review, or a stop.

What would that look like with a task most engineering teams recognise?

Slide 6. How does a result guide the next attempt?

Take a slow test suite.

We time the full suite, find one cause of the delay, and make a small change.

Then we run the same suite again.

If the tests pass but it is still too slow, the new timing tells us where to look next.

The result of one attempt becomes useful input for the next attempt.

What tells this loop when to begin?

Slide 7. When should the work start again?

Sometimes we start it ourselves by submitting a goal.

Sometimes a schedule starts another check, such as an hourly check for documentation changes.

Sometimes new evidence arrives after an alert. An engineer can hand over a fixed log export and start the work.

Once a run starts, it may need several attempts. Starting a new run later is a separate choice.

Which of these ideas are we going to apply to our support assistant?

Slide 8. Which loop are we building?

The support assistant has one job: find approved articles and answer the customer.

We are building an engineering loop around that assistant.

This outer loop checks saved questions, asks for a small code change when needed, and checks the system again.

A useful change waits for review. New questions can start fresh checks later.

How will we know whether one of those changes helped?

Slide 9. What would count as better?

We need to agree on the evidence before we start changing things.

Some checks have a clear rule. The tests pass. The expected article appears first.

Other checks need judgment. An answer can find the right article and still miss an important detail.

For our hands-on example, the automatic check will cover finding the expected source. We will review answer quality separately.

With that distinction in mind, where does another attempt create useful work?

Slide 10. Where does another attempt help?

A fixed error window gives us another reproducible group to investigate.

A loop helps when the last check tells us something useful about what to do next.

Slide 29. 7. Flow control

The watcher looks for new work, but it respects the current review.

If a patch is waiting for a decision, new questions can queue up. The loop waits before making more model calls.

If there is a failure, it has evidence for another bounded repair. If the checks pass, it waits for changed inputs.
