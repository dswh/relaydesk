Build a RAG improvement loop

Your task is to help the assistant find the right help article when a short follow-up depends on an earlier question.

The loop handles repeated checks and repair attempts. You review the proposed change.

Back to the slides · Open the local controller

The question we will follow

“How should our consumer handle duplicate RelayDesk webhook deliveries?”

The next message is: “What should I do next?”

If search sees only that last message, it loses the topic.

The approved webhook article is the expected source. The check asks whether it ranks first in all three retrieval runs.

1. Sensor: save the actual query, returned sources, and answer.

2. Regression protection: compare the same questions and keep every existing pass.

3. Controller: choose one failed question and give Codex its evidence.

4. Actuator: let Codex make a small change in a separate worktree.

5. Runner: run product tests, check all development questions, and then check the frozen patch on other questions.

6. Human feedback: review the answer and patch. Save reusable implementation guidance.

7. Flow control: wait during review. After review, measure the complete question set again.

Start a fresh run

Use the prepared repository on codex/rag-loop-reproducible-demo.

Complete the database, model, and LangSmith setup in the repository’s RAG demo runbook first.

Replace the highlighted run ID with a new name. Reuse that same name in later commands.

pnpm rag:demo prepare --id workshop-01
pnpm rag:demo run --id workshop-01
RAG_REVIEW_PORT=4181 pnpm rag:review

Preparation creates an isolated starting state. The run measures the questions, requests a patch, and checks it.

A failed candidate can lead to another attempt within the fixed limits. A useful candidate waits for your review.

Review what changed

Open the controller. Read the query before and after the change.

Inspect the patch, product test results, and saved answers.

Save a real answer verdict only after reading its evidence. Review the code patch separately.

Add reusable implementation guidance to evaluations/rag-lab/feedback.md. The next repair prompt reads that file.

# After reviewing the code and evidence, choose one:
pnpm rag:demo accept --id workshop-01
pnpm rag:demo reject --id workshop-01

Acceptance chooses the measured local worktree as the next baseline. Release remains a separate decision.

Let new questions restart the check

Start the watcher in one terminal.

pnpm rag:demo watch --id workshop-01

In another terminal, add the prepared question while a patch is still waiting for review.

pnpm rag:demo add-question --id workshop-01 \
  --file evaluations/rag-lab/demo/new-question.json

The watcher waits without model calls during review.

After you accept or reject the patch, it measures a fresh baseline with the new question included.

If a question fails, that evidence can start another bounded repair. At the goal, the watcher waits for changed inputs.

Use Ctrl+C to stop watching. A blocked or bounded run needs attention before repair resumes.

Checks and limits

Questions, approved sources, models, and checks stay fixed during each before-and-after comparison.

The agent can change three RAG files and add focused tests. Each patch has a 100-line limit.

The runner permits three candidates or 20 minutes. The model transport preserves the shared spending cap.

The retrieval goal checks which article search finds. Review answer quality separately.

A broader answer-quality loop needs human labels and a validated judge.
